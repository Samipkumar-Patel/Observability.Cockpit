# LLM & AI Agent Observability for Grafana

Tools for monitoring AI agents and LLM applications in Grafana. This repository contains two projects:

| Project | Folder | Status |
|---|---|---|
| **LLM & Agent Observability Dashboards** | [`llm-observability-dashboards/`](llm-observability-dashboards/) | Early release (v0.1). Recommended starting point. |
| **LLM Observability Data Source plugin** | repository root (`pkg/`, `src/`) | In progress. Backend and query path work; the UI editors are built but need further testing. |

---

## Core Objective & Vision

As companies increasingly build features using Large Language Models (LLMs) and autonomous AI agents (OpenAI, Anthropic, LangChain, CrewAI, n8n, custom pipelines), they face a major blind spot: **traditional monitoring tools (like Prometheus or Datadog) were built for CPU, memory, and HTTP requests, not for AI.**

The goal of this repository is to give engineering teams **native visibility into their AI applications directly inside Grafana**.

---

## What Problems Does It Solve?

When running AI workloads in production, engineering and SRE teams urgently need to track operational metrics that standard APM and monitoring tools completely miss:

1. **Token Consumption & Cost Control:**
   * *Problem:* AI APIs bill strictly by token count (prompt + completion tokens). Without visibility, a single runaway loop in an AI agent can rack up unexpected bills overnight.
   * *Solution:* Tracks token usage per agent and model in real time so teams can set up alerts and dashboards.
2. **Prompt Latency & Performance Regressions:**
   * *Problem:* LLM response times are inherently variable and often slow (taking seconds rather than milliseconds), impacting user experience.
   * *Solution:* Visualizes LLM call duration (p50 and p95) per model to identify slow models or prompts.
3. **Agent Failure Rates & Exceptions:**
   * *Problem:* Autonomous agents frequently fail due to API rate limits (HTTP 429), timeouts, or server errors.
   * *Solution:* Captures error rates by type directly in Grafana alongside infrastructure health.

## Project 1: LLM & Agent Observability Dashboards

Grafana dashboards built on the [OpenTelemetry GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions-genai). They use the existing Prometheus data source, so no custom plugin is needed.

```powershell
cd llm-observability-dashboards
docker compose up -d --build
```

Open **http://localhost:3000** (`admin` / `admin`) and go to **Dashboards > LLM Observability > LLM & Agent Observability**. Wait about a minute for the example app's metrics to appear.

The stack includes an example agent that emits the metrics with simulated calls (no API key needed), an OpenTelemetry Collector, Prometheus, and Grafana. See [`llm-observability-dashboards/README.md`](llm-observability-dashboards/README.md) for the metric reference, architecture, and how to instrument your own app.

## Project 2: LLM Observability Data Source Plugin (in progress)

A Grafana backend data source plugin written in Go. It reads metrics from a local SQLite telemetry file.

### Project Structure

```text
├── llm-observability-dashboards/  # Dashboards project (see above)
├── pkg/                 # Go backend plugin (query handler, health check, SQLite access, unit tests)
├── src/                 # TypeScript frontend (config editor, query editor)
├── dist/                # Generated by build.go and webpack; git-ignored
├── plugin.json          # Grafana plugin metadata (backend: true, executable name)
├── package.json         # Frontend dependencies and build scripts
├── webpack.config.js    # Frontend bundling
├── tsconfig.json        # TypeScript configuration for src/
├── build.go             # Builds the Linux backend binary into dist/
└── telemetry.db         # Local SQLite telemetry file (git-ignored)
```

### Local Testing Guide with Docker

Requirements: Go 1.25+, Node.js 18+, Docker Desktop, PowerShell.

1. **Build the frontend** (writes `dist/module.js`):
   ```powershell
   npm install
   npm run build
   ```
2. **Build the backend** (cross-compiles the Linux binary into `dist/`):
   ```powershell
   go run build.go
   ```
3. **Start Grafana** with the plugin mounted (run from the repository root):
   ```powershell
   docker rm -f grafana
   docker run -d -p 3000:3000 --name=grafana -e "GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS=samipkumar-llm-datasource" -v "$(Get-Item . | Select-Object -ExpandProperty FullName)/dist:/var/lib/grafana/plugins/llm-datasource" -v "$(Get-Item . | Select-Object -ExpandProperty FullName)/plugin.json:/var/lib/grafana/plugins/llm-datasource/plugin.json" -v "$(Get-Item . | Select-Object -ExpandProperty FullName)/telemetry.db:/data/telemetry.db" grafana/grafana:11.4.0
   ```
   Wait about 25 seconds for Grafana to start.
4. **Access Grafana** at `http://localhost:3000` and log in with **`admin`** / **`admin`**.
5. **Add the data source:**
   - Go to **Connections** ➔ **Data sources** ➔ **Add data source**.
   - Search for **LLM Observability Data Source** and select it.
   - Set **Telemetry DB Path** to `/data/telemetry.db` (the path inside the container).
   - Click **Save & test**. Expected result: `LLM Observability data source connected (7 metric rows in /data/telemetry.db)`.
6. **Check backend logs if needed:**
   ```powershell
   docker logs grafana 2>&1 | Select-String "samipkumar"
   ```
   Look for `Plugin registered` and no `Could not start plugin backend` errors.

#### Known limitations
- **Metric names must match the database.** The query editor offers `tokens_consumed` and `prompt_latency_ms`, but the sample `telemetry.db` contains `request_duration_ms` and `orders_processed`. Queries return data only for metric names that exist in the database.
- **Query filter is not applied.** The "Query Filter" field in the query editor is stored but not used by the backend yet.
- The plugin is unsigned, so Grafana logs a warning. This is expected for local development.
